# app-common-python

## Project Overview

app-common-python is a Python client library for accessing [Clowder operator][clowder-operator] configuration in Red Hat Insights applications. It provides a simple API for reading environment-based configuration and accessing Kafka, database, object storage, and service dependency settings. The library is distributed via PyPI and uses schema-driven code generation to stay synchronized with upstream Clowder configuration changes.

## Dependencies

### Runtime Dependencies

- **Python:** 3.10+
- **No external runtime dependencies** — The library uses only Python standard library modules (`json`, `os`, `tempfile`)

### Development and Test Dependencies

- **setuptools** — Build system
- **setuptools_scm[toml]** — Git-tag-based versioning
- **pytest** — Test runner
- **flake8** — Code style linting (configured but NOT enforced in CI)
- **twine** — Distribution validation and PyPI publishing
- **build** — PEP 517 build frontend
- **Podman** — Required for running the code generation script (`sync_config.sh`)
- **yacg** (via Docker image) — Schema-to-Python code generator

See [Development Setup][readme-dev] in the README for the full command reference. Key agent-specific commands:

```sh
python -m venv venv
source venv/bin/activate  # On Windows: venv\Scripts\activate
pip install -e .
```

### Run Tests

```sh
ACG_CONFIG=test.json pytest
```

Tests require the `ACG_CONFIG` environment variable to point to the test fixture file.

### Regenerate Types from Schema

```sh
./sync_config.sh
```

This fetches the latest Clowder JSON schema and regenerates `app_common_python/types.py` using the yacg code generator. Requires Podman.

### Lint Code

```sh
flake8 app_common_python tests
```

Note: flake8 is configured (max line length 100, ignores E128/E811/W503/E203) but NOT run in CI. Linting is optional for contributors.

### Build Distribution

```sh
python -m build -o dist/
```

Produces source distribution and wheel in `dist/`.

### Validate Distribution

```sh
twine check --strict dist/*
```

## Architecture

The library consists of two main modules. The `app_common_python/types.py` file contains schema-generated dataclasses for all configuration types (AppConfig, KafkaConfig, DatabaseConfig, etc.). The `app_common_python/__init__.py` module provides the runtime API: it loads configuration from the `ACG_CONFIG` environment variable at import time, deserializes JSON into a `SmartAppConfig` instance (extended with `rds_ca()` and `kafka_ca()` helpers), and populates convenience dictionaries (`KafkaTopics`, `ObjectBuckets`, `DependencyEndpoints`, `PrivateDependencyEndpoints`, `KafkaServers`) for common lookups.

For a detailed explanation of the schema-driven design, code generation pipeline, and architectural tradeoffs, see the [Architecture documentation][architecture-doc].

## Code Style

- **Linter:** flake8 (configured in `setup.cfg`, NOT enforced in CI)
- **Max Line Length:** 100 characters
- **Ignored Rules:** E128 (continuation line under-indented), E811 (redefinition), W503 (line break before binary operator), E203 (whitespace before colon)
- **Language Version:** Python 3.10+ syntax (minimum supported version)
- **Formatting:** No automated formatter is configured. Follow existing code style in `__init__.py`.

## Common Mistakes

1. **Editing generated code directly.** The `app_common_python/types.py` file is generated by `sync_config.sh` and contains a warning header: "Attention, this file is generated. Manual changes get lost with the next run of the code generation." All edits to type definitions must be made in the upstream Clowder schema, not in `types.py`. If you need to extend generated classes, use inheritance (as `SmartAppConfig` does for `AppConfig`).

2. **Assuming flake8 compliance is required.** The repository includes flake8 configuration in `setup.cfg`, but the CI workflow does NOT run flake8. Suggesting flake8 fixes is helpful but not mandatory for PRs to pass. Check the [CI workflow][ci-workflow] to verify which checks are actually enforced (currently: pytest across Python 3.10+, `twine check --strict`, and successful wheel build).

3. **Not understanding temporary file lifecycle for certificate methods.** The `LoadedConfig.rds_ca()` and `LoadedConfig.kafka_ca()` methods create temporary files using `tempfile.NamedTemporaryFile(delete=False)` and cache the paths in `_rds_ca` and `_kafka_ca` attributes. These files are **not** automatically cleaned up. They persist for the lifetime of the process and are only cleaned by the OS on reboot. This is acceptable for long-running services but could cause disk usage issues if called repeatedly in short-lived CLI tools or test suites.

4. **Expecting runtime errors from missing ACG_CONFIG.** Configuration loading happens at **import time**, not runtime. If `ACG_CONFIG` is unset or points to invalid JSON, the error occurs when `import app_common_python` executes, not when calling API methods. This can cause confusing errors in test environments where the import happens before test fixtures set the environment variable. Use `isClowderEnabled()` to detect whether Clowder is active before accessing `LoadedConfig` attributes.

5. **Forgetting to set ACG_CONFIG when running tests.** The test suite requires `ACG_CONFIG=test.json` to be set as an environment variable. Running `pytest` without this variable will cause import-time errors when the test module loads `app_common_python`. Always run tests with: `ACG_CONFIG=test.json pytest`.

6. **Assuming the schema path in sync_config.sh is correct.** The `sync_config.sh` script changes directory to `pkg/api/v1` before downloading the schema and running yacg. However, this directory does **not exist** in the current repository structure. The script appears to be outdated or intended for a different repository layout. To regenerate types, you may need to adjust the script's working directory or run the Podman command manually from the repository root with corrected volume mounts.

## Testing

Tests are written with pytest and use a static configuration fixture (`test.json`) that contains sample Clowder configuration data. The test suite validates:

- Correct deserialization of all config sections via `dictToObject`
- Population of convenience dictionaries (e.g., `KafkaTopics`, `ObjectBuckets`)
- Temporary file creation for `rds_ca()` and `kafka_ca()`
- `isClowderEnabled()` returns `True` when `ACG_CONFIG` is set

Run tests with:

```sh
ACG_CONFIG=test.json pytest
```

Tests do NOT validate the generated `types.py` code itself (yacg output is assumed correct). They focus on the handwritten runtime logic in `__init__.py`.

## Deployment

The library is published to PyPI automatically on GitHub release events. The CI workflow:

1. Builds source distribution and wheel via `python -m build`
2. Runs pytest across Python 3.10+ with the built wheel
3. Validates distribution metadata with `twine check --strict`
4. Publishes to PyPI using the `pypi_token` secret (on release events only)

Version numbers are derived from git tags via setuptools_scm:
- Tagged commits (e.g., `v1.2.3`) produce version `1.2.3`
- Commits after a tag produce version `1.2.3.devN+gHASH`

To release a new version:

1. Tag the commit: `git tag v1.2.3`
2. Push the tag: `git push origin v1.2.3`
3. Create a GitHub release from the tag
4. CI automatically publishes to PyPI
